# 【E2E 阶段 · Prompt 09】系统级端到端测试与质量闭环（Playwright）

| 项 | 内容 |
|---|---|
| 范式 | E2E：从用户视角验证整个系统（浏览器 → Vite → Express → 引擎 → SQLite → SSE → 浏览器），发现问题后修复并补回归测试，形成质量闭环 |
| 执行者 | luna-worker 子代理（GPT-6 Luna） |
| 编排者 | Factory Droid 主代理 |
| 输入 | `AGENTS.md`、`docs/PRD.md`（验收标准 AC）、`docs/TEST-PLAN.md`（E2E 场景清单）、`docs/API.md`、`docs/UI-DESIGN.md`，以及已完成的 server 与 web |
| 产出 | `playwright.config.ts`、`e2e/**`、根 `package.json` 脚本；为可测试性所做的少量 web / server 改动；`docs/TEST-PLAN.md` 中 E2E 部分的实际结果；审查截图放在仓库外 `C:\Users\123\Desktop\mianshiti\_review\e2e\` |

## 1. 基础设施

- 根目录 `playwright.config.ts`：
  - `testDir: 'e2e'`；`timeout` 90s；`expect.timeout` 15s；`retries: 0`（要靠稳定的等待条件，而不是重试来通过）；`workers: 1`；`reporter: [['list'], ['html', { open: 'never' }]]`；`trace: 'retain-on-failure'`；`screenshot: 'only-on-failure'`。
  - 四个 project（都用 `channel: 'msedge'`）：
    - `desktop`：1440×900
    - `fhd`：1920×1080（评审者最常见的屏幕，会进入 ≥1600 的超宽屏布局）
    - `ultrawide`：2560×1080
    - `mobile`：390×844，`isMobile`、`hasTouch`、`deviceScaleFactor: 3`
  - 功能场景只在 `desktop` 跑，布局场景四个 project 都跑（用 `testMatch` 或 tag 区分）。
  - `webServer` 启动两个进程，端口避开开发默认端口：
    - 后端：`npm run start -w @aps/server`，端口 8790。进程环境变量：`LLM_PROVIDER=mock`、`LLM_API_KEY=sk-test-not-a-real-key`（假 Key，用于泄漏检测）、`DATABASE_PATH` 为系统临时目录下的唯一文件、`MAX_TURNS=8`、`PACING_MS=150`、`MOCK_LATENCY_MS=40`、`MOCK_STREAM_DELAY_MS=20`。
    - 前端：先构建，再用 `vite preview` 监听 5180，`API_PROXY_TARGET=http://127.0.0.1:8790`。若 preview 的代理或 SSE 有问题，可以改用 `vite dev`，并在报告中说明。
    - 都用健康检查 URL 判断就绪；`reuseExistingServer: false`。
  - 进程环境变量优先于 `server/.env`，所以 E2E 永远不会用到真实 Key。请在报告中确认这一点。
- `e2e/tsconfig.json`，并在根目录加 `typecheck:e2e` 脚本。根目录 `typecheck` 脚本要同时覆盖 workspaces 和 e2e（npm 在 Windows 上用 cmd 执行脚本，可以用 `&&`）。
- `e2e/fixtures.ts`：API 辅助函数（通过 `request` 创建、开始、获取快照）、`waitForStatus(page, label)` 等。只用 Playwright 的等待机制（`expect.poll`、`toHaveCount` 等），不要用固定 sleep。唯一例外是验证“一段时间内不再增长”的场景，那里要写明理由。
- 截图：设置了环境变量 `E2E_SHOTS_DIR` 时，把关键画面按 `{场景}-{project}.png` 保存到该目录；未设置时不保存。

## 2. 场景（每个场景在 `docs/TEST-PLAN.md` 中对应到 AC 编号）

1. `lobby.spec.ts`：大厅按“直播中 / 待开播 / 往期回放”分组并显示数量；能看到种子讨论；打开“往期回放”的种子讨论后，Transcript、共识与分歧、总结完整显示（桌面端结束态默认显示“主持人总结”，切换到“共识与分歧”后能看到全部条目及其专家立场），Transcript 中没有“举手 / 抢答 / 准备发言”等内部事件文字。
2. `create-and-live.spec.ts`（主流程）：
   - `/new`：输入 1 个字时出现中文校验提示。输入话题并选择 3 位专家，点击生成，出现骨架屏。
   - 阵容：1 位主持人加 3 位专家，每位都显示姓名、职业 · Title、立场标签和专属色。点击“换一批”后专家姓名发生变化。
   - 换一批失败（AC-F2-7）：用 `page.route` 让下一次换一批请求返回 502（响应体按 API.md 的错误格式，`code` 为 `LLM_ERROR`，message 与服务端文案一致）。页面显示中文错误，专家姓名保持不变，“确认阵容，进入演播厅”仍可点击。取消拦截后确认进入演播厅。
   - 演播厅：
     - Transcript 第一条是主持人开场。
     - 观察到至少一位专家小窗进入“准备发言”（带意图徽标）和“发言中”状态。
     - 字幕条出现流式的部分文本。
     - 在状态变为“已结束”之前，共识或分歧区域已经出现至少 1 条。
   - 结束后：总结至少 2 段；页面上没有 `{"`、`"type"`、`[{` 这类 JSON 痕迹。
   - 导出 Markdown：文件包含话题、阵容和全部发言，且不包含“举手”“抢答”等内部事件。
3. `controls.spec.ts`：开播后点击暂停，状态变为“已暂停”，当前发言完成后发言数不再增长（观察 3 秒）；点击继续后发言数继续增长；点击结束讨论并在二次确认后，状态经“总结中”变为“已结束”，正文发言数小于上限。
4. `isolation.spec.ts`：通过 API 同时创建并开播两场讨论，在两个页面分别打开。两边都结束后：
   - 每个页面 Transcript 中的发言人都属于本场阵容。
   - 每个页面的共识与分歧中，涉及的专家也都属于本场阵容。
   - 通过 API 取快照交叉核对 participantId 和 discussionId。
5. `realtime.spec.ts`：
   - 直播中刷新页面：Transcript 的 seq 不重复、不缺号，讨论继续推进。
   - 用 `context.setOffline(true)` 断网数秒再恢复：连接状态徽标显示重连，恢复后 seq 不重复、不缺号。
6. `layout.spec.ts`（四个 project 都跑）：
   - 大厅、新建页、演播厅（直播中，Transcript 已经溢出）中，页面本身不滚动：`document.scrollingElement.scrollHeight <= innerHeight + 1`。
   - Transcript 等区域可以在自身容器内滚动：设置 `scrollTop` 后页面位置不变。
   - 窄屏下 Tab 能在 实录 / 共识与分歧 / 总结 之间切换。
7. `security.spec.ts`：
   - 打开大厅和演播厅、调用健康检查与快照接口、读取几秒 SSE。期间收集所有响应体（HTML、JS、CSS、JSON、SSE 文本）。
   - 断言其中都不包含假 Key `sk-test-not-a-real-key`、`reasoning_content` 和 `api.deepseek.com`。
8. `discussion-quality.spec.ts`（API 层面，跑完一场后取快照）：
   - 没有同一专家连续两条发言，且专家发言顺序不是按座位轮转。
   - 专家发言与主持人插话 ≤ 2 句，开场 ≤ 3 句。
   - 至少 1 次主持人插话（追问 / 串联 / 点名）；专家发言的 act 至少有 2 种。
   - 达到轮次上限自然结束时，最后一条正文发言来自专家（主持人不在最后一轮提问后无人回答）。
   - 抢答额度（ARCHITECTURE §5.B）：act 为 `interrupt` 的正文发言不超过 `max(1, floor(maxTurns / 6))` 条，且没有两条相邻的正文发言都是 `interrupt`。
   - 总结流式推送：在同一场讨论的 SSE 记录中，act 为 `closing` 的发言有多条 delta，且第一条 delta 早于 `summary.completed`。
9. `real-llm.spec.ts`（可选，默认跳过）：只有设置 `E2E_REAL_LLM=1` 时运行，并用单独的 Playwright 配置或 project 启动不设 `LLM_PROVIDER`、不覆盖 `LLM_API_KEY` 的后端（使用 `server/.env` 的真实 Key）。`MAX_TURNS=8`，走一遍主流程，截图阵容确认、直播中（有人发言且已有共识或分歧）和结束后三张，并记录阵容生成耗时、首条专家发言出现时间和总耗时。本阶段只运行 1 次，用来留存真实模型下的端到端证据。

## 派发补充（编排者，07 续派 3 与 06e 之后）

1. 随机性：E2E 里讨论 ID 每次随机生成，Runner 的 RNG 和 mock 的种子都由它派生，所以每次运行的讨论走向都不同，质量断言必须对任意种子成立。runner 单测已经出现过两次“某些种子下不成立”的偶发失败（洞察更新、专家正文 act 种类），都靠固定种子解决。`discussion-quality` 里“专家发言的 act 至少有 2 种”“结束前出现共识或分歧”这类统计性质，如果只在多数种子下成立，不要靠重试：要么把断言改成规格保证的性质，要么为 E2E 提供确定性（例如服务端读取一个仅供测试、默认关闭的环境变量来固定 mock 与 Runner 的种子），并在报告中说明理由与改动。
2. 07 续派 2、续派 3 之后的引擎行为：抢答额度 `max(1, floor(maxTurns / 6))`（E2E 的 `MAX_TURNS=8` 时为 1 次）；出价返回内容无法解析时重试 1 次；调度增加行为多样性加成（ARCHITECTURE §5.C）。06e 之后 mock 讨论会出现补充与共识。
3. 换一批失败的服务端文案是「换一批失败，已保留当前阵容，可以重试或直接确认开播」；`page.route` 拦截返回的 message 用同一句。
4. §3 的“连续运行 2 次”改为 3 次，都必须全部通过（真实模型场景除外），用来暴露与种子相关的偶发失败。
5. 07b 之后，服务端所有错误响应都带 `details`（没有附加信息时为 `[]`），前端只把符合 API.md §1 的响应体当作服务端错误并展示其 message。`page.route` 返回的 502 响应体要与服务端完全一致：`{ "error": { "code": "LLM_ERROR", "message": "换一批失败，已保留当前阵容，可以重试或直接确认开播", "details": [{ "discussionId": "<当前讨论 ID>" }] } }`。缺少 `details` 的响应体会被前端当作无法识别的数据，这是有意的严格校验，不要为此放宽前端。
6. 主持人串联与追问交替（06e 续派 1 的 G 节，ARCHITECTURE §5.D 第 2 步）：专家连续发言 3 条后，如果最近一次 bridge / follow_up 插话是 bridge，就追问上一位专家；否则有 active 分歧时串联。因此：
   - `discussion-quality` 增加一条只依赖规格、任意种子都成立的断言：按 seq 排列主持人的 bridge 与 follow_up 插话，不会有相邻两次都是 bridge。
   - E2E 后端的 `MAX_TURNS` 由 8 改为 12（与 06e 的整场验收一致）。8 轮内通常只有一次串联，追问几乎不会出现，截图和质量断言都覆盖不到。改为 12 后抢答额度为 2 次，§2 第 8 条的公式不变。真实模型场景仍用 8 轮。
   - 演播厅结束后的审查截图，选一场同时出现串联与追问的讨论；如果借助第 1 条的测试种子来固定，在报告里写明种子和理由。
7. mock 的文本已在 06e 收口（引用取完整主张、开场保留话题的问号、回答主持人时回应对象是主持人、同一议题只有一条分歧等）。E2E 发现 mock 文本的问题只记录现象（截图与原文），不改 `server/src/llm/mock*`。生成审查截图后先自己看一遍：开场与总结里的话题保留问号；引号里的引用是完整的句子、没有“…”；Transcript 中没有“举手 / 抢答 / 准备发言”等内部事件；洞察区每条共识写明双方认同什么，每条分歧写明议题；总结分段，没有 JSON 痕迹。发现的问题写进报告。

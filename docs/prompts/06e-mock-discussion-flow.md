## 现象（摘自 mock-demo-1）、根因与要求

### 1. 观点推进：不再复读立场

- 现象：沈怀瑾三次发言都是“我担心基础任务减少会挤压新人练习”（#3、#6、#11），罗沐言三次都是“我反对把代码生成当作新人替代品”（#4、#10、#13）；其余部分是“还要核实实际影响”“关键条件还没有说清”“不能只凭一个条件下结论”这类不含信息的套话。
- 根因：每个 profile 只有一条 stance，发言模板都是“套话 + 我{stance}”。
- 要求：
  - 每个 profile 增加至少 4 条论据。每条论据是一句具体、能独立成立的观点，角度互不相同（例如适用条件、风险或代价、例子或证据、落地做法），方向与 stance 一致。编程、客服、通用三类话题的全部 profile 都要写；通用 profile 的论据不出现具体行业名词，可以从职业视角出发。
  - 专家第一次发言用 stance 亮明立场；之后每次使用自己下一条还没用过的论据；论据用完后，针对回应对象最近一条发言的具体内容作答（引用仍遵守 06d 的规则）。
  - 删除不含信息的套话尾巴（“还要核实实际影响”“还要把适用条件说清”等）。每条发言 1–2 句，至少包含一个具体内容。
- 断言：一场 12 轮的流程中，每位专家的 stance 原句最多出现 1 次；同一专家任意两条发言的最长公共子串不超过 8 个字；全场没有两条相同的发言。

### 2. 立场方向：要有补充，也要有共识

- 现象：10 轮中 7 条专家发言是 rebut 或 interrupt，没有一次 supplement；洞察区 3 条全是分歧，没有共识。
- 根因与现状：当时 mock 出价按 stanceTag 字符串是否相等判断“相同 / 不同”，而 mock 阵容的 4 个标签各不相同，关系几乎总是“不同”。Prompt 07 已把真实出价和 mock 都改为按立场方向判断（`server/src/prompts/index.ts` 的 `stanceDirection` / `stanceRelation`，mock 中的 `mockStanceRelation`）：含“反对、不支持”等为偏反对；含“支持、认同、看好、乐观”等为偏支持；“中立、观望、谨慎、审慎、保留”为中立；relation 取值为“方向相同 / 方向相反 / 一方中立或谨慎 / 方向不明”。编排者复跑 07 的 mock 全流程时已经出现 1 条共识，但下面的行为还没有测试锁住。
- 要求：
  - mock 沿用与真实出价完全相同的方向分类，不另立规则。mock 不能直接调用 prompts 的内部函数时，保持 `mockStanceRelation` 与 `stanceDirection` 的规则一致，并用测试保证两者对同一批标签给出相同的 relation（例如构造出价 Prompt，读取其中的 relation 文本来对照）。
  - 上一位发言的专家与自己方向相同时，想发言的意图为 supplement；方向相反时为 rebut，偶尔 interrupt（保持 06c 的抢答条件）；一方中立或方向不明时，用确定性哈希在 supplement 与 rebut 之间选择。上一条是主持人发言时保持现状。
  - supplement 的发言要先明确承接对方的论据，再补上自己的论据；洞察据此形成共识。
  - 3 位及以上专家的 mock 阵容中，至少有一对方向相同的专家（按上面的分类判断，用测试锁住）。
- 断言：三类话题各跑一场 12 轮的流程，专家发言的 act 同时包含 supplement 与 rebut；结束时洞察区至少有 1 条共识和 1 条分歧。

### 3. 洞察：写出分歧点，而不是拼接两句立场

- 现象：分歧条目是两句立场原文的拼接（“龚若溪支持助手承担重复编码，沈怀瑾则担心基础任务减少会挤压新人练习”），与下面的专家立场列表重复，读者看不出“分歧点”在哪里；同一句立场原文在 3 条分歧里反复出现。
- 要求：每条论据带一个议题短语（例如“基础任务该不该交给助手”）。洞察的 content 写议题本身，或写成“围绕{议题}，{A}与{B}看法相反 / 一致”；stances 的 position 写各自在这个议题上的具体主张（取自论据，不超过 20 字）。content 不超过 40 字，不含“…”和内部编号，也不能与任何 stance 原句相同。同一对专家围绕同一议题继续交锋时沿用已有 ref（06c 已实现，保持）。

### 4. 主持人：开场不点名，串联问对人

- 开场：mock-demo 的开场说“先请龚若溪从自己的立场说起”，引擎随后由出价选出的却是另一位专家。Prompt 07 已在真实开场 Prompt 中要求不点名，07 续派 1 也删除了 mock 的点名模板。本轮保持：开场点到全部嘉宾后把话交给全场（例如“请各位先亮出判断”），不点名任何人先说。
- bridge：主持人策略的 bridge 目标本来就是分歧中的一方（见 `server/src/core/hostPolicy.ts`），真实 Prompt 的要求是“请目标专家回应另一方”。mock 模板却写成“罗沐言……，沈怀瑾则……。沈怀瑾，请回应双方分歧中的关键条件”。改为：先用一句话点明双方在该议题上的不同，再请目标嘉宾回应另一方，例如“……沈怀瑾，你怎么回应罗沐言的这个判断？”。目标不在双方之中时，沿用现有的通用写法。
- follow_up 与 invite：不要在句中嵌入整句话题，改用“这个问题”，或引用对方的论据。

### 5. 话题嵌入与中英文混排

- 现象：“今天讨论AI 编程工具会如何改变初级软件工程师的培养。”“就AI 编程工具会如何改变初级软件工程师的培养而言，……”“针对AI 编程工具会如何改变初级软件工程师的培养你会先核实什么？”
- 要求：话题整句只出现在开场与总结第一段，写成“今天的话题是：{话题}”或用引号括起来；其他位置用“这个问题”等代称。mock 的全部输出在汉字与拉丁字母或数字相邻处加一个空格；引号、括号和标点旁不加。
- 断言：全部输出不匹配 `/[\u4e00-\u9fff][A-Za-z0-9]|[A-Za-z0-9][\u4e00-\u9fff]/u`；一场 12 轮流程的专家发言中，话题整句出现 0 次。

### 6. 总结：不复读，不重复提问

- 现象：第 2 段把第 1 段的立场原句又说了一遍（“沈怀瑾担心基础任务减少会挤压新人练习”在总结里出现 3 次）；第 3、4 段都是问句，意思重复。
- 要求：① 话题，以及已发言专家各自最有代表性的论据（每人一句，优先用已经说过的论据，而不是 stance 原句）；② 分歧，按议题写，不重复第 ① 段的句子；③ 有共识条目时写共识，没有时写一个开放问题；④ 致谢收尾，第 ③ 段已经是问题时，第 ④ 段不再提问。全文没有重复的分句；至少点名 2 位已发言专家；未发言的嘉宾不得被写成“提到 / 认为”（06c 的要求，保持）。

### 7. 引用不能把对方的立场说反

- 现象（编排者复跑 07 的 mock 全流程）：叶南风说“我反对用自动化替代服务质量评估”，陈文昊接着说“我不同意叶南风提到的‘用自动化替代服务质量评估’”。引用片段确实是原话的连续子串（满足 06d 的规则），但截掉了前面的“反对”，读起来像叶南风主张用自动化替代评估，立场被说反了。
- 要求：引用对方时，如果片段在原话中紧跟在立场词或否定词之后（反对、不支持、担心、担忧、警惕、质疑、不、没有等），引用必须连同这个词一起取，或者改用转述（“叶南风反对用自动化替代服务质量评估，但……”）。rebut 的承接句要针对对方的真实主张，不要对一个否定式的主张再说“不同意”，避免双重否定造成歧义。
- 断言：遍历三类话题的流程输出，每个引号内的引用片段，在被引者原话中紧挨着它的前一个词都不属于上述立场词或否定词。

## 测试（`mock.test.ts`，先红后绿）

- 观点推进：三类话题各跑一场 12 条发言的流程（含 statement、rebut、supplement、interrupt、follow_up、bridge），检查第 1 条要求的三项断言。
- 立场方向：构造同向、反向、含中立三种上一位发言人，分别用多个讨论 ID 出价，同向时不出现 rebut / interrupt，反向时不出现 supplement；3 位及以上专家的阵容中存在同向的一对。

## 派发补充（编排者，07 续派 2、续派 3 之后）

起草本 Prompt 之后，引擎又有三处变化，与 mock 的出价和整场验收直接相关（第 4 条是编排者通读 run-6 后新增的要求）：

1. 抢答额度（07 续派 2）：出价 context 新增 `interruptAvailability: { usedCount, limit, allowed, blockReason }`。mock 只在 `allowed` 为 true 时才可能选择 interrupt（仍保持 06c 的抢答条件），不允许时按 rebut 处理。Runner 会在推送小窗状态前把受限的 interrupt 改写为 rebut，那只是兜底；mock 自己遵守，才和真实模型读到的 Prompt 一致。补一条测试：`allowed` 为 false 时，用多个讨论 ID 出价都不出现 interrupt。
2. 调度的行为多样性加成（07 续派 3，ARCHITECTURE §5.C）：出价对应的发言行为不在最近 3 条专家正文里时加 0.25。第 2 节“同向时想发言的意图为 supplement”配合这一加成，mock 讨论里应能稳定出现补充；整场验收时逐场报告 supplement 正文条数。
3. 出价格式重试（07 续派 3，ARCHITECTURE §8.2）：出价返回内容无法解析时 Runner 会重试 1 次。mock 的 JSON 任务必须始终输出合法 JSON，不要依赖这个重试。
4. 主持人问法不要重复：真实模型的 run-6 里两次串联都问“你怎么回应启航这个说法？”，mock 的第 4 节模板也有同样的风险。bridge、follow_up、invite 各准备至少 3 种问法，用确定性哈希选择；同一场里先用完还没用过的问法，再重复使用。断言：三类话题的 12 轮流程中，主持人发言里以问号结尾的分句两两不同。

测试稳定性：Runner 的 RNG 和 mock 的种子都由每次随机生成的讨论 ID 派生，某些种子下的统计性质可能不成立（runner.test.ts 已有两例：「总结完成前至少推送一次洞察更新」「专家正文发言至少覆盖两种发言行为」，现已固定种子）。因此：

- 新写的整场流程测试使用固定的讨论 ID 和种子，结果不随运行变化。
- 改动 mock 后，如果 runner、api 等现有用例因此失败或偶发失败，先确认 mock 没有违反契约；可以按上面两例的方式固定种子，但不能放宽断言，并在报告中逐条写明。这是本 Prompt“只改 mock 文件”约束的唯一例外。
- “验证”第 2 步改为：`npm test -w @aps/server` 全量连续运行 3 次都通过。

### A. 引用不能截在词中间

现象（三场记录原文）：“可以随时转人工的问题上试”（原话是“……问题上试点自动回复”）、“训练应先让新人自己写出步”“同一句描述可能包含多个需”“新人很难判断生成内容是否”“评估时把谁受益和谁承担成”“担心助手包办基础编码会让”；“反对仓促推广，认为现场差”既跨了分句，又截在词中间。

根因：`shortQuote` 截取固定字数后补“…”，`buildUtterance`、`buildHost` 末尾又用 `.replace(/…/gu, '')` 删掉省略号，只剩半个词（06d 起就存在）。

要求：

1. 引号内只放被引者原话中的一个完整分句。分句以原话首尾和 `，。；：！？` 为界（顿号不算边界），不取原话中引号内的部分（那是别人的话）。分句以“我 + 立场词”开头时可以去掉“我”，但立场词必须保留（06e 第 7 条）。
2. 引用长度 4–20 字（按 `Array.from` 计）。最近一条发言里没有合适的分句时，不加引号，改用被引者论据的 `position` 转述（例如“孟清和反对仓促推广，可是……”），转述同样不能把立场说反。
3. 去掉 `.replace(/…/gu, '')` 这种掩盖截断的做法；mock 的任何输出都不含“…”。

断言（遍历全部模板与 F 节的整场流程）：每个引号内的片段，在被引者原话中，后一个字符是分句标点或原话结尾，前一个字符是原话开头、分句标点或“我”；片段内部不含分句标点；长度 4–20 字；全部输出不含“…”。

### B. 插入的论据、立场和 position 要连成通顺的句子

现象：

- 论据原句直接接在动词后面：“还要看看似简单的问题也可能影响用户权益”“还要看评估时把谁受益和谁承担成本放在同一张表里比较”“具体还要考虑新人仍要独立从报错定位原因”。
- 立场原句缺主语：“我先说明：支持先在规则清楚……”。
- 动词撞在一起：“孟清和更看重反对仓促推广”“龚清越提醒担心复杂诉求无法被及时识别”。
- 议题标签硬套句式：“落到适用范围，……”“可以把问题范围拆开看：……”。
- 反驳看不出不同意：“关于白明月说的“……”，还要看……”只是在追加条件。

要求：

1. 论据原句（`text`）是完整句子，只能出现在句首，或紧跟在 `：，。；` 或连接词（但、可是、不过、而且、因为、所以、其实、毕竟、另外、同时）之后。
2. 以动词开头的立场原句（“支持……”“担心……”“反对……”等）出现在发言里时，前一个字必须是“我”。
3. position 以立场动词开头时（反对、支持、担心、担忧、警惕、质疑、主张、认为、有条件支持等），直接接在人名后面（“孟清和反对仓促推广”），不再套“看重、提醒、强调、认为”之类的动词；不以立场动词开头时才由模板补动词。
4. rebut 先点明对方的主张（引用或转述），再用自己的论据说明它为什么不成立或不够，读者要一眼看出不同意；supplement 先承接对方，再补上自己的论据。rebut、supplement、interrupt 各至少 3 种句式，用确定性哈希选择，同一场先用完没用过的句式。
5. 使用议题短语的模板（statement 开头、bridge、洞察、总结）在换成 C 节的新短语后逐一通读，保证通顺。

断言：每条专家发言中出现的论据原句，前一个字符属于第 1 条的允许集合；全部输出不匹配 `/(?:看重|提醒|强调|认为|主张|关注|指出|觉得)(?:反对|支持|担心|担忧|警惕|质疑|主张|认为|有条件)/u`、`/看看似/u` 与 `/吗[。，；]/u`；立场原句在专家发言中出现时，前一个字是“我”。

### C. 议题短语要看得出争点

现象：论据的议题都是“适用边界、新人练习、复核责任、收益去向、问题范围、适用范围、成本分配”这类泛称；engine-1 的 4 条洞察有 3 条以“围绕适用边界”开头，读者看不出争的是什么。

要求：议题写成能看出争点的短语，4–14 字，例如“哪些任务可以先交给助手”“新人还要不要自己排错”“改动出错谁来负责”“省下的时间用在哪里”；通用 profile 不出现行业名词（例如“试点范围怎么划”“成本由谁承担”“效果用什么衡量”）。同一 profile 的 4 条论据议题互不相同；同一话题组内各 profile 继续共用同一组议题，保证不同专家能就同一议题交锋。

### D. 洞察：写出共同点，人名与立场一致

现象：

- 共识写成“围绕适用边界，周承泽与魏晓峰认可有限共识”，看不出双方认同什么。
- engine-2 结束时只有 1 条分歧，content 写“白明月与龚清越看法不同”，stances 里却有方予安、龚清越、沈向晚、白明月 4 人：不同专家对的条目被合并了。可能的原因是 mock 复用了同一个 ref，或者在不带 ref 时被 core 的 `mergeInsights` 按内容相似度（`similarity` ≥ 0.6）合并；合并时 stances 取并集，content 换成最新一条。

要求：

1. 共识 content 写出双方共同认可的具体内容，例如“韩景明与程以宁都认为成本应与受益对象一并核算”，共同点取被承接一方论据的 position；不超过 40 字，不再出现“认可有限共识”。
2. 分歧只在同一对专家、同一议题时沿用已有 ref（06e 第 3 条的原意）；不同专家对的条目要能被 core 区分开，不能因为 content 只差人名而被相似度合并。

断言（F 节的整场流程，检查 core 合并之后的最终洞察）：每条洞察 content 中出现的专家姓名集合等于其 stances 中的专家集合；洞察 content 两两不同；共识 content 不含“有限共识”。

### E. 主持人和专家的问答要接得上

现象：

- bridge 之后，被点名的专家没有回应另一方：engine-1 #11 请董嘉禾回应周承泽，#12 董嘉禾说“可以把新人练习拆开看：……”，没有提周承泽；engine-2、engine-3 的 #11→#12 一样。
- invite 问“你认为怎样的证据足以支持试行？”，被点名者只是亮立场（engine-1、engine-3 的 #7→#8），没有回答问题。
- 三场的主持插话都是“bridge、invite、bridge”，没有追问，原因见 G。

要求：

1. bridge 之后：被点名专家的出价 replyTo 为 bridge 中的另一方，intent 按与另一方的方向关系决定（同向 supplement，反向 rebut，一方中立或方向不明时用确定性哈希，不选 interrupt）；正文点名另一方，回应其具体主张（遵守 A、B 和 06e 第 7 条）。这一条覆盖 06e 第 2 条中“上一条是主持人发言时保持现状”。
2. invite 点名尚未发言的专家时，问题是请他亮出判断（至少 3 种问法，可以结合他的职业），被点名者用立场作答，读起来是对这个问题的回答；点名已经发言过的专家时（无人出价的情况），请他补充一个新方面，回答用下一条未用过的论据。
3. follow_up 引用或转述被追问者刚说的具体主张，再追问例子、条件或证据之一（至少 3 种问法）；回答用下一条未用过的论据直接作答，不重复立场，不用“我的起点是”“我先说明”之类的开场套话。

断言（F 节的整场流程）：bridge 之后的那条专家发言，replyTo 是 bridge 中的另一方且正文含其姓名；follow_up 之后的那条发言不含发言人的立场原句；invite 点名尚未发言的专家时，之后的那条发言含该专家的立场原句。

### F. 整场流程测试要经过真实调度；补充、共识、抢答要稳定出现

现象：客服话题（engine-2）专家 act 只有 statement 4、rebut 5，没有 supplement，结束时 0 条共识，不满足 06e 第 2 条的整场验收。`mock.test.ts` 的流程测试用的是固定 act 序列，没有经过调度、主持人策略和洞察合并，所以没有发现。三场都没有出现 interrupt。

要求：

1. 新增 `server/src/engine/mockFlow.test.ts`：按 `runner.test.ts` 的方式用 Runner + `createMockProvider` 跑整场，三类话题各 2 个固定讨论 ID（4 位专家，`maxTurns` 12，节奏与延迟设为 0）。原来用固定 act 序列的流程测试可以保留，但 06e 和本续派中的整场断言都要在这 6 场上成立。

3. 抢答：保持 06c 的抢答条件与 `interruptAvailability.allowed` 约束，调整满足条件时的抢答概率，让大多数整场出现 1 次抢答；interrupt 正文要像当场插话，并回应被打断者刚说的具体内容。

### G. 引擎例外：主持人串联与追问交替

### A2. 开场保留话题的问号

现象：r2-4 到 r2-9 的开场是“今天的话题是：城市应该限制网约车数量吗。”“……全面使用 AI 自动回复吗。”；r2-1 到 r2-3 是“今天的话题是：AI 编程工具会如何改变初级软件工程师的培养。”，问号都变成了句号。B 节的 `/吗[。，；]/u` 断言没有覆盖开场。

要求：开场像总结一样把话题原样放进引号，保留原有的结尾标点。总结第 1 段保持 H 节的“今天的话题是“……”。”，开场换一种说法（例如“欢迎来到今天的圆桌，我们来讨论“……？””），两者的第一句不相同。

### B2. 引用短语缺“的”，反驳句式像公文

现象：几乎每条引用都写成“我对苏向晚提到“……”有异议”“我认同周清越提到“……”，并补充”“针对陈南乔提到“……”，我有异议”（r2-1 #3、#4，r2-7 #3）。“X提到“……””在这些句子里作宾语，缺了“的”就不通。r2-1 一场里“有异议”出现了 5 次。

要求：

1. 引用作宾语时写成“X提到的“……””“X说的“……””，或者拆成独立分句“X刚才说“……”，……”。
2. 反驳改用口语句式，例如“X说“……”，这一点我不同意：……”“我和X的看法不一样：……”“X说的“……”我不认同，因为……”。B 节第 4 条（每类至少 3 种句式，同一场先用完没用过的）保持。

断言：全部输出不含“提到“”；每场“有异议”最多出现 1 次。

### C2. 引号里要放能独立成立的主张

现象：

- 复句的后半句：“才能判断哪些操作适合交给助手”（r2-1 #13）、“才能验证试点范围”（r2-4 #13）、“再根据观察结果逐步扩大范围”（r2-8 #4）、“再比较成本是否集中在缺少替代选择的人群”（r2-9 #13）。
- 只有主语的名词短语：“范围清楚又能及时撤回的方案”（r2-7 #4）。
- 缺了主语的谓语：主持人追问中的“可能让可选择空间较小的人承担更多代价”（r2-7 #11），原句的主语“看起来一致的安排”在前一个分句里。
- 其中 4 条又被写进了共识，例如“林向晚与程予安都认同“才能验证试点范围””。

A 节按标点切出的分句满足了“完整分句”的形式要求，但这些分句离开原句就读不懂。

要求：

1. 每条论据和每个立场句在数据里声明一个可引用的主张（例如字段 `claim`）：原文中按 A 节规则切出的一个分句，4–20 字，单独读得懂。可以是完整的主谓句，也可以是原话“我 + 立场动词……”去掉“我”后的部分（例如“支持助手处理规则明确的小改动”）；不能是只有主语的名词短语，不能缺少原句别处的主语，不以依附性的连词或副词开头（才、就、再、并、也、还、而、但、所以、因此、从而、进而、否则、以免、并且、然后、即使、如果、只要、只有、因为、由于等）。原文里没有这样的分句时，改写原文。
2. 专家与主持人引号内的引用（话题本身除外）只能取被引者此前说过的论据或立场的 claim；没有合适的 claim 时，按 A 节第 2 条用 position 转述，不加引号。
3. 共识不再引用原话，见 F2 第 4 条。

断言：数据检查——每个 claim 是对应原文的子串，满足 A 节的边界规则与 4–20 字，不以上面列出的词开头。流程检查（6 场固定 ID）——除话题外，每个引号内的片段都等于被引者在此前发言中已经用过的某个 claim。

### D2. 同一位专家不能复读自己的论据

现象：9 场中有 7 场出现专家把同一条论据原句说两三遍，最长公共子串 24–30 字：r2-1 周清越 #3、#6、#10 三次都说“判断变化时要拆开具体任务看，岗位名称本身不足以代表工作量”；r2-6 董明远 #3、#6、#13 三次都说“试点先覆盖答案稳定的重复咨询，遇到例外就退出自动流程”；r2-3、r2-4、r2-5、r2-7、r2-8 也有。06e 第 1 条要求同一专家任意两条发言的最长公共子串不超过 8 个字，但 mockFlow 的每场检查里没有这一项。看起来是 rebut 按对方的议题去找自己同议题的论据，每次找到的都是同一条，绕过了“用下一条没用过的论据”。

要求：同一场里，每位专家的每条论据和立场句最多用一次；按议题挑论据时，只在没用过的论据里挑。论据全部用完时，按 06e 第 1 条针对对方最近一条发言的具体内容作答，不引入新论据，也不重复自己说过的句子。

断言（加入每场检查）：同一专家任意两条发言的原文（含引号和模板部分）最长公共子串不超过 8 字；每位专家的立场句最多出现 1 次；全场没有两条相同的发言。

### E2. 回答主持人：act、回应对象与内容

现象：

- 9 场的 #12（follow_up 之后被追问者的回答）全部是 supplement、回应对象“未点名”：补充本应承接某位专家，这里没有对象。invite 之后的回答（例如 r2-1、r2-7 的 #8）回应对象也是“未点名”。真实模型的 run-7 中，被追问者的回答是 statement，回应对象是主持人。
- 回答来自按议题共用的 `MOCK_FOLLOW_UP_EVIDENCE`，同一议题无论谁被追问都说同一句；问和答也对不上：r2-1 #11 问“能举个具体例子吗？”，#12 答“把任务类型、人工复核结果和回退次数分开记录，才能判断哪些操作适合交给助手。”，这不是例子。兜底句“还需核对一项可复现条件”没有信息量。

要求：

1. 被 invite 或 follow_up 点名的专家：出价 intent 为 `raise_hand`（正文 act 为 statement），replyTo 为 `H`，urgency 足够高，保证下一条正文就是他。
2. 每条论据增加一条供追问使用的细节（例如字段 `detail: { kind: 'example' | 'condition' | 'evidence', text }`），内容要具体：例子写出具体场景，条件写清在什么情况下成立，证据写明看哪类记录或数据。follow_up 先引用被追问者刚说的那条论据的 claim，再按其 `detail.kind` 提问（例子、条件、证据各至少 2 种问法，仍满足派发补充第 4 条）；回答直接用这条 detail 作答（例如以“比如”“前提是”“可以看”开头），不重复立场，不加开场套话。被追问者上一条只说了立场时，改问他最看重哪一点，回答用他下一条没用过的论据。
3. 删除 `MOCK_FOLLOW_UP_EVIDENCE` 和“还需核对一项可复现条件”兜底，测试里也不再特判这些句子。

断言：每个 invite、follow_up 之后的下一条正文都由被点名者发言，act 为 statement，replyTo 为主持人；follow_up 之后的回答包含所问论据的 detail 原句，提问方式与 `detail.kind` 对应。

### F2. 反驳、补充和洞察要与“在议题上站哪一边”一致

现象：

- 把相容的主张记成分歧：“新人要不要独立排错：魏云舟主张新人独立排错；许以宁要求新人独立拆解”（r2-3）、“用户何时转接人工：邵言川强调复杂情况升级；周书宁主张人工保留处置权”（r2-5）、“苏以宁主张未解决时立即转人工；莫星野主张人工保留处置权”（r2-6）、“梁嘉禾认为新人先独立排错；姚南乔强调团队安排练习”（r2-2）。
- 反驳的理由其实在支持对方：r2-7 #10 高晓峰说“我对陈南乔提到“不同地点的实际条件差异很大”有异议，理由是：看起来一致的安排，可能让可选择空间较小的人承担更多代价”，两人说的都是统一安排有问题。
- 同一议题拆成多条分歧：r2-7 的 4 条分歧都以“试行范围怎么划定：”开头，只是人不同；r2-8 有 3 条。
- 共识写成“都认同“担心……””（r2-6、r2-9），或引用了残句（见 C2）。

根因：论据只标了议题，没有标“在这个议题上站哪一边”。方向只按人（stanceTag）分类，可同一个人的论据可能站在议题的另一边（例如 `mockProfiles.ts` 里“有条件支持”的陈澄，论据“新人仍要独立从报错定位原因”站的是偏谨慎的一边）。mock 按人的方向或哈希决定反驳还是补充，洞察又按发言行为生成，于是出现上面的错位。

要求：

1. 每个议题定义两个相反的取向（简短短语，例如“哪些任务可交给助手”：“低风险任务先交给助手 / 基础任务先让新人自己做”），每条论据标注它站在哪个取向（例如字段 `side`）。方向为支持或反对的 profile，4 条论据的取向都与其方向一致；中立、谨慎的 profile 两种取向都要有。需要时改写论据，仍满足 C 节（议题短语）与 C2。
2. 06e 第 2 条“方向相同 → supplement，方向相反 → rebut（偶尔 interrupt）”保持；“一方中立或方向不明时用确定性哈希选择”改为：按被回应论据所在议题上双方的取向决定，相同 → supplement，相反 → rebut。E 节第 1 条（bridge 之后的回应）同样按该分歧议题上的取向决定。对方上一条只有立场句、没有论据时，仍可用哈希，但选出的论据要满足第 3 条。
3. supplement 只在发言人与被承接者在被承接论据的议题上取向相同时出现；rebut、interrupt 用到的自己的论据，与对方在这条论据的议题上取向相反。没有满足取向条件、又没用过的论据时，出价不选这种行为。
4. 洞察：同一议题最多一条分歧，之后其他专家在这个议题上的交锋沿用同一个 ref、更新 stances。分歧 content 写议题与两个取向（例如“哪些任务可交给助手：低风险任务先交给助手，还是基础任务先让新人自己做”，不超过 40 字），不写人名；stances 的 position 写各自的具体主张，至少包含两种取向。共识 content 写成“A与B都 + 被承接论据的 position”（position 不以立场动词开头时，用“都认为”或“都认同”连接），不再用引号引原话。
5. D 节断言“content 中出现的专家姓名集合等于其 stances 中的专家集合”相应改为：分歧 content 不含专家姓名；共识 content 中的姓名集合等于其参与者集合。

断言（加入每场检查，取向从 profile 数据推导，不靠字符串特判）：每条分歧的 stances 至少包含两种取向；每条共识的参与者在该议题上取向相同；每个议题最多一条分歧；每条 supplement 的发言人与被承接者在被承接论据的议题上取向相同；每条 rebut、interrupt 用到的自己的论据与对方在该议题上的取向相反；共识 content 不含引号。数据检查：支持、反对方向的 profile 的论据取向与方向一致；中立、谨慎的 profile 两种取向都有；每个话题组的每个议题两种取向都有。

### G2. 总结第 2 段不要重复第 1 段

现象：r2-1 第 1 段写“苏向晚反对跳过问题拆解训练；周清越主张按任务类型评估；……”，第 2 段写“分歧主要体现在：哪些任务可交给助手：周清越主张按任务类型评估；苏向晚反对跳过问题拆解训练；严星野支持低风险小改动。”，三个分句原样重复，两个冒号连用；r2-7 第 2 段把 4 个人并列。06e 第 6 条要求全文没有重复的分句，但现在的检查没有按“；”切分。

要求：第 1 段保持“姓名 + position”。第 2 段每个分歧议题（最多 2 个）只写取向不同的两方各一位代表（优先选证据发言多的），写他们实际说过的 claim，不写 position，例如“分歧主要在“哪些任务可交给助手”上：周清越认为岗位名称本身不足以代表工作量，苏向晚则担心新人很难判断生成内容是否答非所问。”

断言：总结按 `，。；：！？` 切分后没有重复的分句；第 2 段每个议题最多出现 2 个人名；同一句里不出现两个冒号（不匹配 `/：[^。！？\n]*：/u`）。
